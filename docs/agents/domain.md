# Domain docs

Before changing domain behavior, read `CONTEXT-MAP.md`, the relevant context's `CONTEXT.md`, and any relevant decision in `docs/adr/` or that context's `docs/adr/`. If a file does not exist yet, proceed; domain-modeling creates it when a term or decision is resolved.

Use the glossary's terms in tickets, APIs, UI copy, and tests. Surface a conflict with an existing ADR instead of silently overriding it.

The context map names the product responsibilities and points to their glossaries. Keep implementation details in ADRs or specs, not in a glossary.
